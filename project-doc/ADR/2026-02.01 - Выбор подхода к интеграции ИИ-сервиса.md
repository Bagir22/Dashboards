**Дата:** 24 февраля 2026 г.

**Статус:** Принято

**Контекст:**

Функциональность ИИ-помощника требует интеграции с внешним или внутренним ИИ-сервисом для генерации текстового анализа на основе данных дашборда. Генерация может занимать значительное время (секунды), и мы не должны блокировать пользовательский интерфейс на это время. Также необходимо обрабатывать сценарии недоступности сервиса или недостатка данных.

**Рассмотренные варианты:**

- Синхронный запрос (Request-Response): Фронтенд отправляет запрос к ИИ-сервису и ждет ответа, блокируя UI (показывая лоадер). Если сервис отвечает долго, пользователь не может взаимодействовать с дашбордом.
- Асинхронный запрос с поллингом (Polling): Фронтенд отправляет запрос на создание задачи генерации. Сервис сразу возвращает ID задачи и закрывает соединение. Фронтенд периодически опрашивает другой эндпоинт, проверяя статус задачи и получая результат, когда он готов.
- WebSocket / Server-Sent Events (SSE): После запроса на генерацию устанавливается постоянное соединение (WebSocket) или открывается SSE-канал, через который сервер сам присылает результат, как только он готов.

**Решение:**

Выбран асинхронный запрос с поллингом (Polling) как компромисс между сложностью и пользовательским опытом.

**Обоснование:**

- Нет блокировки UI: Пользователь может продолжать работать с дашбордом, пока генерируется ответ. Лоадер отображается только в том окне, где будет показан результат.
- Простота реализации на бэкенде: Бэкенду не нужно управлять долгоживущими соединениями (WebSocket) для тысяч пользователей. Достаточно реализовать механизм фоновых задач и пару эндпоинтов: POST /api/ai/analyze (создать задачу) и GET /api/ai/task/{id} (получить результат). Это проще в разработке и отладке, не требует управления очередями как отдельной инфраструктурой.
- Устойчивость к ошибкам: Легко обрабатывать таймауты и ошибки ИИ-сервиса. Если фоновая задача завершается с ошибкой, мы можем вернуть соответствующий статус при следующем поллинге.
- Меньше нагрузки при простое: В отличие от WebSocket, поллинг не требует поддержания постоянного соединения, если пользователь не ждет ответа или закрыл окно.

**Последствия:**

- Необходимо спроектировать API для асинхронной работы.
- На бэкенде потребуется механизм фоновых задач (например, с использованием пула потоков или воркеров) и хранилище для результатов на время, пока пользователь их не заберет (например, in-memory кэш или временная таблица в БД).
- На фронтенде нужно реализовать логику поллинга с учетом отмены запроса, если пользователь закрыл окно с анализом.
- Объем передаваемых данных от фронтенда к ИИ-сервису (метаданные, данные виджетов, фильтры) должен быть оптимизирован, чтобы не перегружать сеть. Возможно, потребуется передавать не сами данные, а ссылки на них или их хеши.
